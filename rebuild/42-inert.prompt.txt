`inert` removes a subtree from hit-testing and from focus. That is the whole
explanation. `closeCase()` was never broken; the button never receives the event,
the wheel goes to the page behind, and focus never enters. Setting
`case-wrap.inert=false` by hand immediately makes `elementFromPoint` return the
button and the wheel scroll the sheet to 400.

Two more measurements from the same session:

    after opening, document.activeElement    BODY        (focus never moves in)
    three Tab presses                        focus leaves the dialog entirely
    #case-box aria-modal                     "true"

So a screen-reader user is told the rest of the page is hidden, and is then placed
nowhere.

Escape working is the clue to the shape of the bug. Its listener is registered on
`document` with capture, so it is never inside the inert subtree and keeps firing.
Everything that has to be aimed at the sheet - a click, a wheel, a focus - is
routed by hit-testing, and hit-testing is what `inert` switches off. The keyboard
route out survives; every pointer route in is gone.

There is a second cause of the same symptom. `id="tip"` is declared twice on the
page. `tipEl` resolves to one of the two, so the other is a body child that this
same loop inerts, which is why `DIV#tip` appears in that list despite being named
in the guard.

# What to build instead

One dialog. Decide which of the two implementations owns the sheet and delete the
other; do not leave both running and reconcile them.

The overlay owns the scroll. The card sits inside it. That is already written
down in your own comment at line 6997, and it is the right decision - keep it.

The guard on the inert loop must be about containment, not identity. Anything
that contains the sheet is part of the sheet. An element captured at boot is a
stale handle the moment another block re-parents it, and identity comparisons
against stale handles fail silently, which is exactly what happened here.

Give the tooltip a name of its own so that `getElementById` returns the element
the code means. Two elements with one id is not a style question; it made a live
control unreachable.

The dialog must be operable by someone who never touches a mouse:
  - opening moves focus into the sheet
  - Escape closes it
  - Tab cycles inside it and does not escape
  - closing returns focus to whatever opened it

Do not solve this by removing `inert` and leaving the page behind clickable. The
inerting is correct; only its guard is wrong. A dialog that claims `aria-modal`
and leaves the page behind live is a worse answer than the bug.

While you are in the sheet: the action bar is narrower than the panel it sits in.
It renders x 298 to 831 inside a panel spanning x 280 to 1160, leaving a visible
step at its right edge. Its rule assumes a panel padding that the other overlay
stylesheet no longer supplies:

`#case-wrap` is styled in three places, with two different open mechanisms
